# Full review, November 2026 (v0.5.2)

A review of the whole code base, documents and architecture at v0.5.2 (not only a branch
diff), with a profiling run of the demo. The twenty worst things found, ranked by real impact,
and what was done about each.

## Baseline

- 340 unit and integration tests pass in 27 s; branch coverage **99.21 %** (gate 95 %).
- Profiling (demo, 21 monitored people, 32 accounts): a full selected refresh takes 1.2 s; every
  read endpoint answers in 2 to 25 ms (`/api/dashboard` 15 ms, 283 KB, 25 KB gzipped; team
  report 14 ms; meeting summary for 30 days 14 ms). The reads are not the bottleneck; the
  findings below are about correctness, robustness and wasted work.

### 1. Cross-site requests can change shared state (CSRF)

`POST /api/teams/{id}/apply` and `POST /api/refresh` have no body, so any web page the user
visits can send them as a plain form post to `http://127.0.0.1:8000`. Verified: a request with
`Origin: https://evil.example` and `Sec-Fetch-Site: cross-site` replaced the shared selection
(HTTP 200). **Fix:** a middleware rejects unsafe methods (POST, PUT, PATCH, DELETE) with 403 when
`Sec-Fetch-Site` is `cross-site` or `same-site`, or when an `Origin` header names another host
than the request. Tools without these headers (curl, scripts) keep working.

### 2. Any `Host` header is served: DNS rebinding

A page on an attacker's domain can rebind that name to `127.0.0.1` and read every API response
(names, work, time logs) because the app answers any `Host`. **Fix:** `TEAMPULSE_ALLOWED_HOSTS`
(comma-separated). When it is empty and the app binds to a loopback address, only `localhost`,
`127.0.0.1` and `[::1]` are accepted; otherwise any host (servers behind a proxy set the
variable). Other hosts get 400.

### 3. A passing epic failure fails the whole work dataset

`SyncService._epics` only caught `GitLabCapabilityError`. A GraphQL timeout, rate limit or 5xx
on the optional epic query propagated out of `fetch()`, so the person's issues and merge requests
were not refreshed either and the card turned red, although epics are documented as best effort.
**Fix:** any other `GitLabError` (except authentication) keeps the stored epics (last known good)
and logs a warning; issues and merge requests still refresh.

### 4. The single scheduler owner is not enforced

Two `serve` processes, or `gitlab-team-pulse refresh` while the server runs, crawl the same
database twice and race on the same rows; the rule lived only in documentation and the Gunicorn
worker count. **Fix:** an advisory lock file next to the database (`<db>.lock`, `fcntl.flock`).
The scheduler only starts when it holds the lock (otherwise the app serves the cache and records
a diagnostic); `refresh` refuses to run while another process holds it.

### 5. A hung request stops the poll loop for good

`api.js` used `fetch` without a timeout, and `App.poll` schedules the next poll only after the
request settles. A request stuck on a half-open connection (laptop sleep, VPN switch) froze the
dashboard silently. **Fix:** every request is aborted after 20 s (`AbortSignal.timeout`), which
the poll loop treats as offline and retries.

### 6. The dashboard is refetched on every sync step during a refresh

Each sync step bumps `data_version`; during a refresh the browser polls every 2 s and refetched
the whole dashboard (283 KB for 21 people) on each bump, for every open tab. **Fix:** while the
crawler is refreshing, the dashboard reloads at most every 10 s; the final state loads as soon as
the refresh ends.

### 7. Polls can overlap and render out of order

`pollSoon()` (tab visible again, selection changed) started a new poll even while one was still
in flight, so two polls could fetch and render concurrently. **Fix:** a poll that is requested
while another runs is remembered and runs right after it.

### 8. A busy `VACUUM` reports a failed cleanup that succeeded

The hourly cleanup commits retention, then runs `VACUUM` in the same `try`. When a sync write
held the database, `VACUUM` failed with "database is locked" and the whole cleanup was recorded as
failed. **Fix:** a failed `VACUUM` is logged and retried on the next cleanup; it no longer turns a
committed cleanup into an error.

### 9. Timelog paging truncates silently

`GitLabClient.get_user_timelogs` stopped after `max_pages` without a word. For the timelog
history backfill that stores the missing oldest days as zero hours, which the event history
already prevents with `complete=True`. **Fix:** hitting the page cap raises, so the dataset fails
and keeps its last known good state.

### 10. Project lookups bump `data_version` when nothing changed

`_resolve_projects` committed and bumped `data_version` even when every lookup failed, so every
open browser refetched the full dashboard for nothing. **Fix:** it bumps only when it stored a
project.

### 11. "7 days" is hard-coded

Card labels, tooltips, the subtitle and panel titles said "7 days" although
`TEAMPULSE_ACTIVITY_DAYS` accepts 1 to 31 and the server counts over that window. **Fix:** the
labels use the window from the payload.

### 12. Validation errors show as "[object Object]"

FastAPI returns validation errors as a list in `detail`; `api.js` turned it into a string, so
toasts read "[object Object]". **Fix:** list details are joined from their `msg` fields.

### 13. Four settings are missing from the README

`TEAMPULSE_CLEANUP_INTERVAL_SECONDS`,
`TEAMPULSE_SCHEDULER_TICK_SECONDS`, `TEAMPULSE_SCHEDULER_ENABLED` and the Gunicorn
`TEAMPULSE_FORWARDED_ALLOW_IPS` were undocumented. **Fix:** documented, and a test now fails when
a `Settings` field is missing from the configuration table.

### 14. Log redaction misses exception tracebacks

`RedactingFilter` rewrote only the message; the traceback text of `log.exception` was printed
unredacted. **Fix:** redaction happens on the fully formatted line, traceback included.

### 15. The relative-time ticker runs in hidden tabs

Every second the app queried and rewrote every relative time in the document, also in a
background tab. **Fix:** the ticker skips hidden documents and catches up when the tab is shown.

### 16. The work upsert looks items up without a usable index

`replace_user_work` looked records up by `gitlab_id IN (…)`; the only index is the unique
`(kind, gitlab_id)`, which that filter cannot use, so each user's write scanned the table.
**Fix:** the lookup filters by `(kind, gitlab_id)` pairs and uses the unique index.

### 17. A failed directory call leaves the other request running

`sync_directory` gathered `current_user()` and `list_users()`; when one failed (for example
401), the other kept paging through all accounts. **Fix:** the sibling request is cancelled.

### 18. Activity deduplication rebuilds a set per event

The first activity sync rebuilt the set of known event IDs for every older event (quadratic).
**Fix:** the set is built once.

### 19. The token file is read on every status poll

`Settings.gitlab_configured` read the token file from disk on every `/api/status`,
`/api/dashboard` and `/api/health` call (every 2 to 20 s per open browser). **Fix:** the status
payloads report the configuration the process started with; the file is read once.

### 20. Sync writes SQLite on the event loop thread (documented)

Sync steps commit through synchronous SQLAlchemy sessions on the asyncio loop, so a write
briefly blocks async request handlers. Measured on the demo, each write takes a few
milliseconds and a full refresh of 21 people 1.2 s, so moving writes to a thread (with the extra
locking it needs) is not worth its risk now. Revisit if refreshes of many people make the UI
lag; the note is in `docs/ARCHITECTURE.md`.
